## Key Code Changes

- `main.py::AutoSyncManager.reset_after_barrier()` / `Api._reset_manual_sync_state()`: force-clear in-flight guard state (`is_syncing`/`_sync_lock`, `_manual_sync_in_progress`) synchronously on the Qt main thread right after `pause_barrier()` returns — safe because both the barrier call and the guard-state mutations only ever happen on that same thread.
- `main.py`'s two result-handling slots (`_on_auto_sync_result`, `_on_manual_sync_result`) both gained an explicit `if stage != "batch": ... return` guard before the batch-handling code, closing the fall-through that let an unrecognized stage register as a false success.
- `attendance.py::search_employee()`: three-tier prefix ranking (`first_name_prefix_results`, `other_prefix_results`, `contains_results`) replacing the old single `exact_results` tier that mixed "starts with" and "contains anywhere" and hit its 10-result cap in cache-iteration order.
- `web/script.js`: added `lookupActiveIndex` + `setLookupActiveIndex()` to track and move a highlighted result row; `lookupResults.scrollTop = 0` reset in `showLookupOverlay()`; `isLookupOverlayOpen()` check inserted into the global `Escape`/click-outside handlers ahead of the app-close fallback.

## What Could Improve

- On the first search-ranking fix attempt, I split matches into "prefix" vs "contains" but didn't distinguish first-name-prefix from surname-prefix — that gap was only caught because the user tested again and reported the "j → Parichart" case. A more careful first pass (checking against a roster with realistic first/last name variety, not just a two-name synthetic example) might have caught this without a second round-trip.

## Lessons Learned

- **Pattern**: When ranking/ordering search or filter results, "prefix match" is not a single tier — first-word-prefix and later-word-prefix (e.g. first-name vs surname) can conflict for the same query, and users expect first-word priority. Test with realistic multi-field name data, not just a two-name synthetic pair, to catch this class of ranking bug the first time.
- **Discovery**: This machine has at least three distinct Python installations capable of running this app (sandbox default 3.14 without PyQt6, a standalone 3.12 with PyQt6, and the project's own `.venv` 3.12 with PyQt6) — always check which one a command actually used (`.venv/Scripts/python.exe` vs bare `python`) rather than assuming PATH resolution matches intent, especially when a user reports a `ModuleNotFoundError` that "shouldn't" happen.
- **Pattern**: Before relaunching a GUI app in this environment, check `Get-CimInstance Win32_Process -Filter "Name='python.exe'"` (not just `tasklist`, which omits the command line) for already-running instances — multiple instances against the same SQLite file is a real, recurring risk here, not a one-off.
- **Pattern**: A global keyboard/click handler that special-cases some overlays (admin, dashboard) but not a newer one (lookup) will silently misroute events for the missed overlay — when adding a new modal/overlay, grep the codebase for existing overlay-handling branches (`Escape`, click-outside) and add the new overlay to all of them, not just its own open/close functions.
