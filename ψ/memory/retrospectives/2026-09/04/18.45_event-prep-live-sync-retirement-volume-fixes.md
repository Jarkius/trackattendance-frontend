### Key Code Changes

- **Clear-data barrier reordering** (#89): `admin_clear_station_data()`/`admin_clear_cloud_data()` raised the sync coordinator's pause barrier only before the *local* SQLite clear, after the cloud delete's own network round-trip had already run — a real race where an in-flight auto-sync upload could resurrect rows the admin panel just reported as cleared. Fixed by moving the barrier to the top of each method. Found by direct code review, not a user report — verified with a new regression test that fails against the pre-fix ordering.
- **`.env` export rewrite** (#91): the original settings-export button (#87) regenerated `.env` from a fixed template, silently deleting every comment and any setting the template didn't enumerate. Found live when the user's hand-tuned, heavily-commented `.env` was reduced to 55 bare lines after one click. Rewritten to edit matching `KEY=value` lines in place, preserving everything else.
- **Duplicate-window clamp mismatch** (#93): `config.py` capped `.env`-loaded values at 3600s, but the admin panel's "Always" preset sent 86400s — so a fresh station (no SQLite override yet, per `deploy.bat`'s clean-install design) silently downgraded 86400→3600, landing on a value with no matching UI preset. Found live during the actual 10-laptop rollout, would have affected every station.
- **Barcode double-fire root cause** (#95, the core incident of this session): post-event report review surfaced ~30 corrupted badge scans (e.g. `108670108670`) concentrated on 2 of 10 stations. Traced via each station's raw log to: those two stations had `LIVE_SYNC_ENABLED=True` (contrary to plan), and `submitScan()` only cleared the barcode input field *after* the Python bridge callback returned — so a scanner double-fire during Live Sync's cross-station network wait landed on the still-full field and concatenated. Fixed by clearing the field immediately on Enter, before the bridge call.
- **Live Sync retirement** (#96): removed the synchronous cross-station duplicate check entirely (root cause of #95) and the fire-and-forget immediate-upload half that rode alongside it. Added a "Deduplicated Attendance" sheet to `dashboard.py`'s Excel export as the after-the-fact replacement for what Live Sync used to catch in real time.
- **Volume control, two iterations** (#98 → #100): first shipped a separate "Max System Volume" admin button (Windows Core Audio via `pycaw`) after a user report that 100% on the app's own slider was still quiet on one station (Windows system volume was at 36%, and `QAudioOutput.setVolume()` can never exceed the OS ceiling). User pushed back — "why a second button, make the existing slider do it" — reworked same-day so the existing Volume slider drives Windows' system volume directly and proportionally, removing the standalone button entirely.
- **Immediate Write** (uncommitted): revived, in stripped-down form, the one *safe* half of the retired Live Sync feature — the fire-and-forget `sync_single_scan()` upload that never touched SQLite and was never part of the blocking chain. Explicitly excluded the unsafe half (the synchronous duplicate check). Gated behind a new admin toggle, off by default.

### Architecture Decisions

- **Reviving `sync_single_scan()` after just retiring the feature it belonged to** — deliberate, not contradictory. The decision was scoped narrowly by tracing the actual removal commit (`git show a71e2b4^`) to confirm which half of the old code caused the production bug (the synchronous duplicate check) versus which half was independently safe (the fire-and-forget upload, verified to never touch `self.db` and never block the caller). Alternative considered and rejected: building a new mechanism from scratch instead of reviving old code — rejected because the old `sync_single_scan()` was already proven correct in production before removal, and rebuilding it fresh would have been strictly more risk for no benefit.
- **Volume control ownership: one slider, not slider + button** — user explicitly rejected the two-control design after it shipped and was documented. Consequence: had to walk back an already-merged, already-documented feature (#98/#99) same-day, including editing the CHANGELOG/README entries for a version that had already been released, rather than bumping the version again for what was really a design correction.

## Lessons Learned

- **Pattern**: When retiring a feature because of a specific, traceable bug, explicitly separate "what caused the bug" from "what else this feature did that was independently safe" before deciding whether any part of it is worth reviving later — confirmed by diffing the actual removal commit rather than trusting memory of what the feature "was."
- **Mistake**: Don't ship a new UI control for a problem that an existing control could plausibly absorb without first asking the user which shape they want — a single clarifying question before implementation is cheaper than a same-day design reversal after.
- **Discovery**: A concentrated failure pattern across a subset of otherwise-identical stations (2 of 10, not spread evenly) is a strong signal to check *configuration divergence* between those stations before reaching for a hardware explanation — the actual cause here was that only those two had a feature flag enabled that the rest of the fleet didn't.
